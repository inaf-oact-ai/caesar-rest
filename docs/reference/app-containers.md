# Scientific application containers

CAESAR-REST executes scientific applications through containerized jobs submitted to the configured execution backend.

The scientific application code and its dependencies are packaged separately from the CAESAR-REST web application. CAESAR-REST validates job requests, selects the configured scientific application container and delegates execution to the scheduler.

This guide documents the scientific container inventory, container image configuration, Singularity/Apptainer usage and relevant compatibility considerations.

For command-line options, see the [CLI reference](cli-options.md). For execution infrastructure, see the [deployment guides](../deployment/index.md).

## 1. Container execution architecture

CAESAR-REST supports different execution backends:

| Backend | Container execution approach | Status |
| --- | --- | --- |
| Slurm | Singularity/Apptainer-compatible SIF images | Recommended |
| Kubernetes | OCI/Docker-compatible container images | Secondary backend |
| Celery | Historical container execution integration | Legacy/deprecated |

In a typical Slurm deployment:

1. A client submits a scientific job through the REST API.
2. CAESAR-REST validates the application, options and input resources.
3. The corresponding application configurator prepares the execution arguments.
4. The Slurm integration submits a job referencing the configured container image.
5. The scientific container executes in the cluster environment.
6. Job monitoring updates execution status and records output availability.

For staged scientific pipelines, additional mechanisms handle run reservations, immutable upstream artifact bindings and retained scientific outputs.

The container image supplies the scientific execution environment; it does not replace CAESAR-REST's authentication, dataset authorization or pipeline lifecycle management.

### 2.3 OxKAT

OxKAT is integrated into CAESAR-REST through its application-specific configurator.

The current web application parser exposes:

```text
--oxkat_container
```

Its default image path is:

```text
/opt/containers/oxkat/oxkat-caesar.sif
```

OxKAT is used for staged radio-interferometric scientific processing and supports stage-specific configuration validation.

The scientific pipeline may require retained upstream directories and files, rather than only a standalone input file.

The exact supported stages, input contracts and scientific configuration options depend on the installed OxKAT configurator and container.

The Docker registry image name for the current OxKAT container is not established by the historical image inventory in this document. Consult the OxKAT image build and deployment configuration used by the target environment.

## 3. Configuring container image paths

For Slurm execution, CAESAR-REST uses container image paths configured through `apps/run_app.py`.

For example:

```bash
python apps/run_app.py \
	--job_scheduler=slurm \
	--caesar_container=/opt/containers/caesar/caesar-job_latest.sif \
	--fextractor_chronos_container=/opt/containers/fextractor/fextractor-chronos_latest.sif \
	--oxkat_container=/opt/containers/oxkat/oxkat-caesar.sif
```

This illustrates container-related arguments only; it is not a complete production deployment command.

Container paths must refer to images accessible in the execution environment.

In particular:

- The specified image must exist and be readable.
- The Slurm execution nodes must be able to access the image through the appropriate filesystem or path mapping.
- The container must contain the expected scientific scripts and dependencies.
- Input data, models, job directories and retained artifacts must be accessible through the required mounts.
- GPU-dependent applications must have compatible cluster resources and container runtime support.

Parser defaults are fallback paths, not evidence that an image is installed.

See [Slurm deployment](../deployment/slurm.md) for cluster configuration details.

## 4. Creating Singularity/Apptainer images

Scientific application containers can be distributed as OCI images and converted into Singularity/Apptainer SIF files.

For example, using Apptainer:

```bash
apptainer pull caesar-job.sif docker://sriggi/caesar-job:latest
```

Or using Singularity:

```bash
singularity pull caesar-job.sif docker://sriggi/caesar-job:latest
```

These commands illustrate image conversion syntax using a historical repository name. They require the referenced image and tag to exist in the registry.

For reproducible production deployments, use a tested immutable image digest or a specific release tag rather than relying on `latest`.

Once an image has been generated, place it in the directory visible to the scheduler and configure its path in CAESAR-REST.

### Test the image

Before registering an image for production jobs, verify that the container runtime can read it:

```bash
apptainer inspect /opt/containers/caesar/caesar-job_latest.sif
```

The following command can test the container's execution environment, assuming a shell is available in the image:

```bash
apptainer exec /opt/containers/caesar/caesar-job_latest.sif /bin/sh -c 'echo Container execution OK'
```

A successful inspection or shell test does not prove that the application's scientific workflow will execute correctly.

Application-specific smoke tests should also verify the expected command-line interface, dependencies, model accessibility and output generation.

## 5. Container storage and bind mounts

Scientific applications often require access to storage outside the container image.

Typical resources include:

- Uploaded data and managed scientific datasets.
- Job working and output directories.
- Pretrained model files.
- Scientific configuration and auxiliary files.
- Pipeline artifacts retained from upstream stages.

Slurm execution nodes must see the expected paths.

Where container bind mounts are required, the source and destination paths must match the execution scripts and the cluster's storage configuration.

The CAESAR-REST container image options identify the executable images; they do not automatically guarantee that all required data directories are mounted.

For managed datasets, the authorization layer resolves dataset IDs to permitted server-side resources. Clients should not bypass this mechanism by supplying arbitrary paths within managed dataset roots.

For Pipeline V2, retained artifact bindings provide the approved mechanism for consuming upstream scientific outputs.

See [Dataset management API](../api/data.md) and [Pipeline artifact retention](../deployment/artifact-retention.md).

## 6. Troubleshooting Singularity/Apptainer storage

### 6.1 Image conversion cache and temporary space

Pulling or converting large images can require substantial cache and temporary disk space.

With Singularity, the historical configuration variables are:

```bash
export SINGULARITY_CACHEDIR=/path/to/large/cache
export SINGULARITY_TMPDIR=/path/to/large/tmp
```

Apptainer installations normally use:

```bash
export APPTAINER_CACHEDIR=/path/to/large/cache
export APPTAINER_TMPDIR=/path/to/large/tmp
```

Create these directories before using them and ensure they are writable by the account performing image operations.

For example:

```bash
mkdir -p /storage/container-cache /storage/container-tmp

export APPTAINER_CACHEDIR=/storage/container-cache
export APPTAINER_TMPDIR=/storage/container-tmp
```

These variables are particularly useful when the user's home directory or the system temporary filesystem has limited capacity.

### 6.2 No space left on device during execution

A container may fail with:

```text
OSError: [Errno 28] No space left on device
```

This does not necessarily mean that the persistent filesystem is full.

Possible causes include:

- Insufficient temporary storage.
- A full container cache.
- Exhausted filesystem capacity or inodes.
- A session directory or writable temporary filesystem size limit.
- Scientific outputs being written inside a container's temporary writable layer instead of a suitable bind-mounted output directory.

The original CAESAR-REST documentation noted that older Singularity installations could require increasing `sessiondir max size` in the Singularity configuration file, historically located at:

```text
/usr/local/etc/singularity/singularity.conf
```

The relevant setting and configuration path depend on the installed Singularity/Apptainer version and site configuration.

Before increasing container runtime limits, verify that large scientific outputs are written to an appropriate bind-mounted filesystem and check the available disk capacity, inodes and temporary storage.

Changes to system-wide container runtime configuration should be coordinated with cluster administrators.

## 7. Kubernetes container considerations

The Kubernetes backend uses container images through its cluster execution integration rather than the Slurm SIF paths.

Its requirements include:

- Container images accessible to the Kubernetes nodes.
- Appropriate registry credentials when using private registries.
- Correct filesystem or remote-storage configuration.
- Pod permissions and resource limits.
- Compatible application execution arguments.

The historical CAESAR-REST repository includes Kubernetes-related configuration and Celery-oriented manifests that may not reflect the current deployment architecture.

Kubernetes support should therefore be treated as a secondary integration until the selected deployment configuration has been validated.

See [Kubernetes deployment](../deployment/kubernetes.md).

## 8. Compatibility and maintenance

The historical `sriggi/*` image names are preserved because they document the evolution of the scientific application ecosystem.

They should not be interpreted as a guaranteed catalog of available or currently maintained images.

Likewise, the presence of a container-path option in `apps/run_app.py` does not guarantee that the corresponding scientific software has been installed or tested on a given Slurm cluster.

For reliable deployments, maintain a local inventory of tested image versions, paths and scientific application compatibility.

Container updates should be coordinated with the relevant CAESAR-REST application configurator and execution scripts.

This is especially important for scientific applications that depend on particular framework versions, model weights, external command-line tools or structured pipeline artifacts.
